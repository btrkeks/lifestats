# Evidence and review method

## Sources and confidence

Observed implementation means an inspected source path or recorded read-only
runtime observation. A source-derived failure path is not described as a
reproduced production incident. Recorded intent requires an explicit commit,
design note, or comment; mechanics alone do not establish author intent.
Design recommendations are proposals, not descriptions of deployed behavior.

The baseline and user-confirmed requirements are in [brief.md](brief.md). The
machine-readable inventory is generated by [inventory.py](inventory.py). Its
output describes declarations; it cannot tell whether an excluded package is
unused in a user's workflow or whether a deployed executable matches HEAD.

## Investigation roles

- Domain/application: product invariants, public Rust interfaces, orchestration,
  and ownership of calculations.
- Persistence/ingestion: atomicity, concurrent writes, retries, source identity,
  progress, sessions, and source integration boundaries.
- API/consumers: HTTP contracts, TypeScript clients, web UI, mobile integration,
  and representative loggers.
- History/deployment: refactor lineage, explicit tradeoffs, Cargo's actual
  workspace membership, checked-in deployment units, and read-only live status.

Investigators may write only separate scratch reports. They do not edit the
repository, restart services, or write to the live database. The orchestrator
owns the report artifacts. Candidates inspect the same grounding and brief and
write to independent scratch directories. An independent Codex reviewer examines the result and decision trail. The user
ruled out Claude after its failed synthesis attempt; there is no cross-model
review in the completed process.

## Required distinctions

- Intended layers versus the implemented dependency graph.
- In-process Rust calls versus HTTP calls versus deployed processes.
- Active Cargo workspace members versus excluded manifests and vendored apps.
- Authoritative server product state versus client-owned collection state,
  cached reads, pending writes, and provisional presentation.
- Generic observation ingestion versus integration-specific source translation.
- Stored facts versus derived views; durable notifications versus optional
  best-effort reactions.

## Verification boundary

The inventory is rerun and compared for deterministic output at the same source
revision. Report source references are checked against the actual files. HTML
is checked at desktop and phone widths before publication. Existing behavior is
verified only where explicitly stated in the report; static inspections are
labeled. No refactor, database migration, production write, or mobile proof
slice is claimed by this review.

The next implementation milestone must exercise the chosen contract with two
independent consumers against isolated storage, including duplicate retries,
stale edits, source corrections, server restart, and concurrent updates.

## Recorded artifact verification

The inventory rerun remained identical after report assembly. Static checks
validated 40 source citations, local links, unique IDs, and seven tab/panel
relationships. Browser previews at 728px light and 360px dark exercised every
tab and measured each panel with its details expanded, with no horizontal
overflow. Both final screenshots were visually inspected. The initial dark
preview exposed a backdrop contrast problem; the report now uses the host
theme background. See `evidence/browser-qa.json` and the final static check.
These checks concern the report, not the proposed application.
