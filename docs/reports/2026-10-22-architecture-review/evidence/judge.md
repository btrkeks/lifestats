## Base, rubric, and exact grafts

**Select Candidate A's capability-owned server with bounded in-transaction loading and pure decisions.** Both candidates independently converge on this ownership shape; their principal substantive difference is transaction execution. SQLite's single-writer model and this workload favor A's smaller correctness argument. Capability packaging can follow demonstrated ownership inside existing crates.

1. **Invariant/write ownership:** A strong; B strong. Both hide repositories and keep canonical calculations with capability owners. B's binary-private modules make external access especially clear; A's library/storage-contract seam needs an explicit dependency allowlist and construction restrictions. Neither proposal alone proves enforcement. Prefer A without exposing its transaction vocabulary to HTTP or loggers.
2. **Atomicity, replay, corrections, deletion:** A stronger initial fit; B viable but unnecessarily intricate. A loads authoritative state inside the transaction. B must validate metadata, binding epochs, negative lookups, contribution phantoms and range versions, then distinguish internal replanning from caller conflicts. Both correctly require atomic receipts/effects/change records and retained deletion identity. Their guarantees depend on migrating every writer.
3. **Compact executable contract:** Both strong direction, incomplete verification. One typed submit boundary hides workflow; generated versioned wire DTOs avoid domain/transport leakage. A explicitly addresses int64 encoding; B better specifies errors and scoped synchronization. No generated contract or real HTTP conformance proof exists yet.
4. **Incremental, caller-safe adoption:** Both sound with explicit scope fencing. A gives the clearest baseline takeover rule; B explicitly prevents rollback to old direct writers. Neither may infer installed caller retirement from Cargo membership. Legacy routes cannot manufacture missing client identity or ordering.
5. **Operational simplicity:** A wins. One server, SQLite, synchronous bounded work, existing collectors and no mandatory broker match one user. B's optimistic commit framework adds machinery without measured need.

**Exactly two grafts from B:** (1) scope-owned snapshot/cursor synchronization, including consistent watermarks, deletion reconciliation and empty-page scan progress; (2) installation-generation and publisher-epoch fencing, including device restore/transfer. Preserve A's receipt binding, canonical reads and baseline reconciliation. `design.md` largely implements this synthesis as a proposal.

**Reject:** B's optimistic read-set/replan machinery initially; microservices, business event sourcing, generic mutation/plugin frameworks and full local calculation replication. Do not make durable online heartbeat leases a prerequisite for the confirmed offline-fact contract. Static per-device/source grants can implement authorization without a tenancy platform.

## Prioritized changes before publishing the recommendation

These are **design/report blockers**, not requests to implement the refactor now.

**P0 — Reconcile the HTML snapshot protocol with the selected design.** Contracts currently require `expectedRevision: knownRevision` and advise fetching/resubmitting on conflict; both candidates instead use persistent source revisions. This is not interchangeable. Old snapshot 17 can fetch the server version after clear 18 and overwrite it if automatically rebased. Use `(stream, authorityEpoch, day, sourceRevision)`, higher/lower/equal rules, retained clear tombstones, and atomic bounded batches. Keep expected server versions for human edits/corrections. A genuinely refreshed source snapshot gets a new operation identity; retrying old content does not. Update finding 5, contract table, examples and migration language together. `design.md` already makes the distinction correctly.

**P0 — Put receipt lookup inside the atomic boundary.** HTML sequence step 2 precedes the transaction in step 3. A preflight lookup may optimize, but receipt identity must be rechecked under the same immediate write transaction as canonical reads, effects, receipt and cursor. State bounded size/time limits and whole-transaction busy retry. An absent receipt must not allow two requests to execute effects. `design.md` fixes the placement but does not explicitly name immediate acquisition.

**P1 — Freeze immutable operation scope.** Carry `design.md`'s installation-generation key and canonical payload binding into HTML. Bind actor/grant scope, destination, intent/schema version and every precondition. Define stored outcomes for unchanged/stale/conflict, while transient failures leave no acceptance receipt. Choose installation-lifetime compact identities initially, rather than HTML's unspecified replay lifetime. Attempted envelopes never change. A destination switch keeps old queued work in its original namespace; it cannot silently retarget it.

**P1 — Make baseline takeover executable as a decision.** HTML correctly warns against double counting, but needs the stronger selected rule: per statistic/day/source scope, keep the opaque baseline, or atomically adopt/replace a verified exclusive baseline; ambiguous mixed provenance blocks automatic backfill. Fence legacy aggregate writers before contribution merging starts. Replaying a migration/backfill must reach the same state. Preserve IDs and codec fixtures. This is a cutover gate, not a promise to reconstruct lost provenance.

**P1 — Publish cache/restore semantics completely.** Carry scoped cursors, fixed scan upper watermark and empty-page advancement into HTML. Newly cached scopes need their own snapshot. Atomically replace a complete scope, including absent/deleted rows, with its watermark; a paginated snapshot needs consistent paging or a restart rule. Reject older racing responses. Goal schedule changes invalidate affected date ranges and dependent summaries; day rollover needs expiry. Server restore must change generation through an operational restore procedure, even when backed-up metadata contains the old generation. Pause ambiguous old-generation writes for reconciliation and retain drafts. A new generation does not recover acknowledged operations/receipts lost since backup.

**P1 — Specify goal versions and integer wire values.** A daily override revision alone misses concurrent default edits while inheriting. A goal edit token must cover override presence/suppression and applicable default schedule, including no-goal state. Schedule edits need their own conditional version and explicit effective interval. Preserve explicit overrides and invalidate every affected canonical view. Use validated decimal strings or explicit safe bounds for *all* 64-bit wire fields, including counters, goals and revisions, not only observation amounts. Keep cursors opaque. Update numeric examples accordingly.

**P2 — Align sequence and session scope.** Goal revision/history and canonical-read behavior cannot first be settled in phase 4 after their transport/write schemas freeze in phases 1–2. Specify them early; implement the minimal canonical read with the proof slice. Sessions remain a product decision: queued completed intervals are durable facts; a heartbeat acknowledgment currently is not durable activity acknowledgment. If durable online capture is later selected, define last acknowledged endpoint, fencing, expiry and restart without downtime credit. Preserve existing consumers until that separate migration.
