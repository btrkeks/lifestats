Lifestats architecture review · 22 October 2026 · Proposed design

One server owns authoritative writes.
Product modules own their rules.

Keep a modular Rust server and SQLite. Strengthen its public application boundary, move independently deployed loggers onto HTTP, and share a generated client contract across frontends. Build the React Native app on cached queries and a durable command queue.

The immediate problem is inconsistent guarantees between writers and consumers. A folder reorganization alone cannot make an offline retry safe, preserve a source correction, or prevent a stale goal edit.

Confirmed scope. One user, multiple devices and loggers. Mobile caches reads and queues writes offline. Full offline replication, multi-user tenancy, and a microservice deployment are outside the initial design.

Own bounded items and absolute checkpoints. Preserve latest versus furthest position and positive-frontier daily deltas. Effective-date queries and explicit historical as-of queries are separate concepts.

Own stable source identity and translate source input into product intents. Shared write orchestration binds a receipt to its payload and commits all required effects. Connector-specific OAuth and extraction stay in adapters.

Commit operation receipt, state changes, resource revisions, and cache-change sequence together. Preserve imported legacy aggregates with explicit unknown provenance. Only the server opens and migrates this database after direct writers retire.

External source connections

Own vendor communication and credentials. Keep presentation dependencies out of product composition. Add durable background delivery only for a required downstream consumer; the cache change log does not require business event sourcing.

Plotting is disposable presentation. Product queries return values, units, goal state, and authoritative calculations. React Native draws interactive charts locally. The optional image frontend preserves Obsidian embeds and current styling. Removing it must not change product rules, storage, or mobile query contracts.

Make these boundaries enforceable

  • Public application operations accept an identity and typed intent. They load canonical state internally and return an outcome. Callers cannot supply a repository, transaction connection, or unrelated loaded statistic.
  • Product code cannot import Axum, Diesel adapters, or concrete plotters. Capability internals stay private. Crates or import checks enforce the selected package boundaries.
  • One executable transport schema defines the wire contract. Generate the OpenAPI document and TypeScript models/codecs from it, then validate real server responses against that contract.
  • Every accepted write has explicit duplicate, stale, conflict, deletion, and retry semantics. Old APIs keep their documented limitations until their actual callers migrate.

The first implementation milestone

Repair the reproduced interval and numeric defects, establish contract fixtures, then prove one additive observation and one source-day replacement through the server using two independent consumers. Require duplicate retries, stale clears, concurrent writes, and restart tests against isolated storage before promising offline delivery.

Three representative flows

Manual daily addition
  1. HTTP loads the statistic and parses a string according to its type.
  2. The handler reads current JSON, calculates a new value, and separately saves it.
  3. A notification is published after saving. The default publisher drops it.
  4. A later query resolves goals and calculates achievement. There is no transaction spanning the initial read and save, or operation ID covering a retry.
LiftLog edit, move, and clear
  1. The phone updates workouts and queues affected dates in the same local transaction.
  2. A send rebuilds full days from current workouts. Matching-sequence acknowledgement preserves edits made during a send.
  3. The server normalizes intervals and replaces only named days. An empty named day clears its value.
  4. Server days commit individually. No source revision rejects an old delayed request. The accepted limitation explicitly assumes one phone.

Recorded delivery limitation

Ebook event and absolute progress
  1. A stable event ID reaches ingestion.
  2. One transaction records its receipt and increments a daily total.
  3. A separate operation resolves the book, adjusts a target, and appends an idempotent checkpoint.
  4. An identical retry can repair missing progress. The receipt does not cover all effects atomically or reject different content under the same identity.

Priority reflects the confirmed offline and multiple-device requirements. A reproduced library defect is distinct from a possible failure schedule or a production incident.

2. Overachievement can become a failed goal
Reproduced in actual core

An at-least goal of 10 with value 30 returns 44%, because 300 is narrowed to a byte. The same percentage type represents bounded efficiency and potentially unbounded achievement.

4. Generic writes have neither atomic mutation nor replay identity
Static call pathSynthetic schema schedule

Read–calculate–save uses separate repository calls. Two reads of zero followed by two calculated replacements can leave one. Retrying an accepted additive write can count twice. The schema experiment demonstrates that schedule's outcome, not a concurrent Rust or production execution.

Commit a bound operation receipt and the mutation atomically. Retain source ownership where corrections must preserve other contributors. Migrate MIDI before claiming exclusive server write ownership.

5. An old source snapshot can undo an edit or clear
Recorded accepted limitation

LiftLog's sequence protects local acknowledgements and is not sent to the server. Arrival order determines accepted daily state. Old requests can replace newer content; two phones have no authority rule.

Use a server-registered stream, publisher epoch, and persistent source revision per day. Lower revisions are stale; equal revisions with changed content conflict. Retain clear tombstones. A new device cannot invent a stream or rebase old content to replace a newer clear.

6. Default-goal edits can change past applicability
Static data flowProduct decision required

Changing a default resets its valid-since date to local today and updates metadata separately from the sole default value. Earlier days can become no-goal days. There is no stale-edit precondition.

Propose effective-dated goal history with explicit retroactive correction. Preserve daily override, suppression, and return-to-default semantics. Import surviving history honestly; overwritten goals cannot be reconstructed.

New applicability dateHistorical resolution

7. Source identity and receipts do not cover every required effect
Static transaction boundaries

Provisioning is lookup-then-create without a unique source binding. Ebook commits the receipt and total before progress. It can reuse an ID with changed content without binding the complete effect. The schema also permits orphan daily rows and numeric ID reuse.

Uniquely bind source/context/metric independently of display tags. Bind receipts to immutable destination and payload. Commit required effects together or persist pending work from the accepted payload. Preserve public IDs through tombstones or durable non-reuse.

8. Live sessions and effective dates have narrower guarantees
Static path; incidence unknown

Heartbeat start checks existence rather than statistic type. Workers choose the current date and keep registry state in memory. Progress delta queries mix effective-date ranges with recorded-time cutoffs, so late uploads can change which range contains a contribution.

Validate capture type, keep endpoint timestamps, and choose explicit interval attribution. Persist offline source interval facts instead of replaying live heartbeats. Treat daily history and historical as-of queries separately.

Dependency and contract observation

The application calls a concrete timeline renderer with image dimensions. Generic plot conversion recognizes specific Fitbit tags as seconds. Error handling sometimes turns input errors into 500, and extraction errors do not have one public shape.

Atomic write sequence

  1. Authenticate a device, authorize its source binding, and construct validated domain input. Enforce the advertised batch, record, and payload size limits.
  2. Begin an immediate SQLite write transaction. Find the operation receipt inside that transaction; bind the destination, actor grants, schema version, preconditions, and canonical payload.
  3. For a new operation, load canonical target state inside the same transaction, check its type and authority/version, and apply the complete operation.
  4. Persist required product effects, receipt, revisions, and change records together. Store unchanged, stale, and conflict outcomes without effects. A transient failure rolls back without an acceptance receipt.
  5. Reply only after commit. A lost response retries the identical envelope. Busy retries rerun the whole transaction within a bounded deadline.

The contract advertises batch-day, record-count, payload-byte, and transaction-work limits. Oversized requests fail before mutation. The storage adapter implements this bounded write transaction. Load canonical state and run pure decisions inside it; do not fetch network data there. Product ports name complete typed operations and do not expose SQL connections. Busy retries rerun the entire transaction. Bounded multi-day batches commit all named days or none.

Operation identity is scoped to the server installation generation. Bind authenticated actor, destination, schema version, preconditions, and canonical semantic payload. Keep compact identity receipts for that installation lifetime initially. Restoring a backup changes generation and pauses ambiguous client writes for reconciliation; a client must not invent fresh IDs and blindly replay work whose old receipts may have been lost.

A snapshot source persists its per-day counters across restarts and acknowledgements. Device restore or publisher transfer obtains a new server-granted authority epoch that fences former publishers. User goal edits use expected server versions, including the inherited default schedule. These two version protocols are distinct. A device clock is not a global ordering authority.

Source facts, legacy data, and calculation ownership

New ingestion retains enough source identity to correct or clear its own contribution. For metrics with multiple contributors, define aggregation explicitly: sum compatible amounts, union intervals, or designate one authoritative stream. Separate unrelated measurements rather than merging them by display name.

Keep legacy daily values as a clearly marked baseline with unknown provenance. Do not count that baseline together with a backfill of the same source. For each migration scope, keep the opaque baseline or atomically adopt a verified exclusive-source baseline. Ambiguous mixed provenance blocks automatic backfill. Fence legacy aggregate writers before contribution merging starts; repeating the same takeover reaches the same state. Do not enable new live scopes while an old direct database writer can bypass that fence.

Statistics own units, canonical interval normalization, missing-value semantics, goal history, and achievement. Progress owns checkpoint semantics. Source adapters own detection and interpretation such as a bedtime evening date or completed workout. Every accepted timestamp has an explicit effective date; DST elapsed time and wall-clock display are separate.

Client queue and cache

Each normalized read scope owns its snapshot and cursor. Start with bounded complete snapshots whose data and watermark share one read transaction. Split oversized scopes explicitly; a future paginated protocol must pin a consistent snapshot or require restart. Feed pages scan to a fixed upper watermark and advance even when no matching change is returned. A newly cached scope obtains its own snapshot.

Install updates and their cursor atomically. Discard older racing responses. A full refresh replaces the complete scope, including absent and deleted rows, while preserving the independent outbox. Goal schedule edits invalidate every affected range and summary. Time-dependent views carry expiry and refresh at day rollover.

A server restore procedure must mint a new installation generation even if the restored metadata contains an old one. Clients retain pending work but pause ambiguous old-generation writes for reconciliation. The protocol cannot recover accepted operations or receipts lost after the backup.

  • Persist an immutable intent and stable ID before sending. Local pending state survives restart. A changed intent gets a new ID.
  • Order replacements within a stream. Keep a conditional acknowledgement so an in-flight send cannot erase a later local edit.
  • Show cached freshness and pending status. Provisional UI values do not become authoritative product calculations.
  • Clear or rebase the cache on destination changes. Retain pending work in its original destination/account namespace.
  • Keep compact deduplication identities for the installation lifetime initially. Any future retirement must reject expired identities rather than treating them as fresh.

Product data and optional plotting

Keep canonical queries independent of images and chart libraries. Return typed values, units, intervals, goals, and achievement. The image frontend maps those into its existing colors, axes, labels, and PNG layout; React Native independently maps them into interactive chart models. Date/interval aggregation belongs to product queries; zoom, touch behavior, and visual downsampling belong to presentation.

The current /plot/data includes chart choices and styling, so preserve it only as a presentation compatibility API where still used. Do not turn it into the permanent mobile contract. Keep existing image/timeline URLs working for Obsidian. The optional image frontend can call the public query interface in-process; no separate service is needed. Core packages need neither plotting imports nor a renderer port.

Public errors and contract authority

Use stable codes for validation, unsupported capability, duplicate-payload mismatch, stale revision, not found/deleted, rate limit, and temporary failure. Supply field errors, current revision where safe, and retry timing. Preserve rejected commands for user action; do not discard a queue entry merely because some 4xx occurred.

Encode all 64-bit wire integers, including goals, source counters, and resource revisions, as validated decimal strings; cursors remain opaque. Propose Rust transport DTOs as the schema authority, with generated OpenAPI and TypeScript artifacts. Domain structs remain independent of HTTP. A route/schema check and response fixtures cover the null default, all three override states, valid type-specific policies, and every error class. Test the web UI and logger examples against the same contract before RN adopts it.

Single-user operation still needs a deployment identity decision. Keep a private-network setup if desired, but specify device/source authorization. Fitbit OAuth authorizes Fitbit; it does not authenticate a Lifestats caller. Do not claim the current API is publicly exposed without deployment evidence.

Migrate by demonstrated guarantees

Each phase has a behavior gate. Renaming modules is useful only when it makes a prohibited dependency or invalid operation fail a check.

Phase 0 · Baseline and containment

Freeze actual behavior and repair deterministic defects

Keep representative nonprivate fixtures for legacy values, goal tri-state, source receipts, and IDs. Fix interval panic/validation and percentage wrap. Expose supported capabilities; do not advertise unfinished derived behavior.

Gate. Repeated valid intervals do not panic. Overachievement remains achievement. Totals and achievements agree on canonical input. Existing valid payloads still decode.

Phase 1 · One public contract

Establish typed application operations and transport fixtures

Hide raw repositories from new callers. Specify goal history and revision tokens, canonical daily reads, errors, metadata units/capabilities, and explicit time attribution before their schemas freeze. Generate the transport contract and client models. Repair SDK goal and policy behavior.

Gate. Real HTTP fixture responses validate against the generated schema. Shared client preserves all goal states. Invalid application/adapter imports fail. No new writer uses read/save orchestration.

Phase 2 · Durable write semantics

Add receipts, source bindings, revisions, and change records

Use additive schema migrations. Bind identities to immutable payloads and authorized destinations. Add effective-dated goal history and the minimal canonical read for the proof slice. Execute required multi-module effects in one transaction. Resolve existing duplicate source identities and legacy baselines without dropping history.

Gate. Two consumers prove response-loss retries, conflicting ID reuse, concurrent additions, stale replacement/clear, source correction, deletion, and server restart against isolated SQLite.

Phase 3 · Migrate actual writers

Remove competing database ownership

Move MIDI to a transport client. Inventory installed copies of other writers. Adapt LiftLog, ebook, Anki, and scheduled sources to explicit new semantics. Preserve old routes until each active caller has moved; keep their limitations explicit.

Gate. Only the server has database/migration access. New clients cannot import bootstrap/persistence. Compatibility adapters call the same product operations. No legacy caller silently acquires stronger delivery guarantees.

Phase 4 · Canonical queries and offline proof

Build the minimal RN path on a proven contract

Complete the remaining canonical range reads and progress effective-date behavior against the semantics fixed in phases 1 and 2. Put cache, outbox, and sync state transitions outside React presentation. Introduce a consistent bootstrap/refetch watermark and deletion-aware reconciliation.

Gate. Mobile-style local queue plus a logger operate against the same isolated API. Restart, timeout, cursor expiry, destination change, and pending goal conflict preserve work. Server and both clients agree on authoritative results.

Phase 5 · Complete boundary enforcement

Move modules where the verified ownership requires it

Finish capability packaging and remove internal bypasses, concrete renderer dependencies, retired compatibility paths, and misleading templates. Keep query calculation shared. Place the static-image frontend outside product code, preserve representative image fixtures, and keep image routes optional. Source capture remains separate. Removing images must leave mobile queries and product storage unchanged.

Gate. Add one sample frontend and one logger without SQLite knowledge or duplicated product calculations. CI rejects forbidden imports and stale generated contracts. Every retired path has a migrated caller inventory.

Compatibility checks need copies. The existing compatibility test applies migrations to its configured snapshot. Run it on a copy, then expand coverage beyond metadata to values, goals, receipt replay, progress, and deletion. Never use the live snapshot as a read-only check.

Product choices to settle before schema implementation

  • Default changes apply from an explicit date; propose preserving prior history. Define the UI for an intentional retroactive correction.
  • Choose one authoritative LiftLog stream initially. A second phone needs explicit transfer or record-level sharing. A new publisher must reconcile server-accepted days and clears; a new epoch alone cannot make a stale backup authoritative.
  • Specify how source contributions combine for each metric. Do not add duplicate snapshot totals together.
  • Define a recoverable conflict UI. Initial compact identity retention is fixed for the installation lifetime; future retirement must reject expired identities explicitly.
  • Define timestamp/day rules for midnight, DST, and source-specific activity days. Keep the original instant alongside explicit attribution when available.
